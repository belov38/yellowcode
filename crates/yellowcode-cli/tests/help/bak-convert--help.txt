Сохранить CF, DT или 1CD из копии MS SQL Server: через сервер (--server) или, только CF, прямым чтением файла

Usage: yellowcode bak convert [OPTIONS] --to <TO> --output <OUTPUT> <SOURCE>

Arguments:
  <SOURCE>  Путь к BAK: с --server — на машине SQL Server, без --server — локальный файл

Options:
      --platform-build <BUILD>
          Точная версия эмулируемой платформы (не режим совместимости конфигурации) [default: 8.5.1.1529]
      --server <SERVER>
          Сервер для sqlcmd -S: имя или адрес машины, имя\экземпляр или имя,порт (см. «Подключение к SQL Server» ниже); без него CF читается из файла напрямую
      --backup-set <BACKUP_SET>
          Номер набора резервной копии в BAK (позиция из RESTORE HEADERONLY) [default: 1]
      --progress <MODE>
          Ход работы в stderr: auto — строка на терминале, always — строки для журнала, never — без него (по умолчанию переменная YELLOWCODE_PROGRESS, иначе auto) [possible values: auto, always, never]
      --to <TO>
          Формат результата [possible values: cf, dt, 1cd]
      --output <OUTPUT>
          Путь к новому файлу на машине с Yellowcode
      --user <USER>
          SQL-логин; пароль только из переменной SQLCMDPASSWORD; без --user — доверенное подключение (Windows-аутентификация)
      --sqlcmd <SQLCMD>
          Путь к Microsoft sqlcmd (ODBC); по умолчанию sqlcmd
      --sqlcmd-lifecycle-timeout <SQLCMD_LIFECYCLE_TIMEOUT>
          Общий срок каждой команды sqlcmd в секундах (по умолчанию 1800 + 120 на остановку); очистка получает отдельный срок
      --trust-server-certificate
          Доверять сертификату SQL Server без проверки его цепочки (нужно для самоподписанного сертификата, например в Docker)
      --trace <FILE>
          Записать трассу выполнения в новый файл и при успехе (или задайте переменную YELLOWCODE_TRACE)
      --memory-limit <MEMORY_LIMIT>
          Только для 1CD: бюджет памяти восстановления DT (auto или B/KiB/MiB/GiB); не ограничивает MS SQL Server
      --raw
          Только для CF: вернуть CONFIG как он хранится в базе, не применяя остатки динамического обновления
      --strict
          Только без --server: отказать, если CF нельзя доказать равным восстановленному SQL Server (журнал не применён, ADR, другая версия SQL Server), вместо предупреждения
      --ignore-extra-tables
          Только для DT и 1CD с --server: пропустить сторонние не-1С таблицы в схеме dbo (отсутствующие таблицы 1С и двойники расширений X<N> не пропускаются)
  -h, --help
          Print help

Копия восстанавливается во временную базу на вашем SQL Server, результат выгружается на машину с Yellowcode, временная база удаляется. Без --server CF читается прямо из файла BAK, без SQL Server.

Что нужно для работы с --server:
  - Microsoft sqlcmd на ODBC (пакет mssql-tools18 или mssql-tools) на машине с Yellowcode; go-sqlcmd не подходит;
  - логин с ролью sysadmin: команда должна уметь удалить временную базу, поэтому без этой роли она отказывает сразу, до создания базы;
  - место на сервере под всю базу, данные и журнал, даже если нужна только конфигурация;
  - SOURCE — путь к BAK так, как его видит служба SQL Server на машине сервера: Yellowcode файл не копирует.

Примеры:
  # CF через SQL Server: Windows, локальный именованный экземпляр, доверенное подключение
  yellowcode bak convert 'C:\Backup\base.bak' --server localhost\SQL2022 --to cf --output base.cf

  # CF без SQL Server: прямое чтение локального файла копии
  yellowcode bak convert base.bak --to cf --output base.cf

  # DT: Linux, SQL Server 2022 в Docker на той же машине, SQL-логин; каталог с копией смонтирован в контейнер как /backup
  SQLCMDPASSWORD='<пароль>' yellowcode bak convert /backup/base.bak --server 127.0.0.1 --user sa --trust-server-certificate --to dt --output base.dt

  # 1CD: новая файловая база (каталог new-base создать заранее), 4 ГиБ памяти на загрузку DT
  SQLCMDPASSWORD='<пароль>' yellowcode bak convert /backup/base.bak --server 127.0.0.1 --user sa --trust-server-certificate --to 1cd --output new-base/1Cv8.1CD --memory-limit 4GiB

Что получается:
  CF — из полной копии, в том числе сжатой. Если конфигурацию обновляли динамически, CF такой же, как выгрузка Конфигуратора; с --raw — как конфигурация хранится в базе. На копиях баз типовых конфигураций записи CF совпадают с выгрузкой Конфигуратора 8.5.1.
  CF без --server: если копия полная, несжатая, одним файлом, сделана SQL Server 2022 без нагрузки на базу, без ускоренного восстановления (ADR) и с контрольными суммами журнала, CF совпадает с CF через сервер (в ответе proven: true). Иначе CF всё равно пишется (кроме отклоняемых копий, см. ниже), а в stderr выводится строка предупреждения с причиной: журнал копии в этом режиме не применяется. --strict вместо предупреждения отказывает; точный вид даёт --server.
  DT и 1CD — для баз с управляемыми блокировками, в том числе типовых конфигураций на БСП с режимом совместимости 8.3.14–8.5.1, копии которых записаны платформой 8.5.1. В предварительной проверке на 9 копиях типовых конфигураций DT, построенный по этим правилам, совпал с выгрузкой Конфигуратора (/DumpIB) той же копии по содержимому таблиц, и платформа его загрузила; приёмка текущей сборки не закончена, поэтому ответ DT и 1CD помечен "experimental": true. 1CD — загрузка того же DT в новую файловую базу; загрузка открывает базу для проверки под бюджетом --memory-limit, и проверочному открытию базам уровня УНФ нужно около 1792 МиБ, уровня ERP около 3 ГиБ.
  Пользователи переносятся. Адреса почты пользователей не переносятся, как и в выгрузке платформы: результат пишется, в stderr — предупреждение с числом пользователей с адресом, в ответе — usersWithEmail. В 1CD пользователи конфигурации без разделения пользователей пересобираются при загрузке DT; вход таких пользователей платформой ещё не принят.
  Расширения конфигурации (ConfigCAS и блок хранения SchemaStorage SchemaID 1 с таблицами X1) переносятся в DT (число таблиц расширений — extensionTables в ответе); в 1CD блок расширений загружается в рамках поддерживаемого профиля восстановления.

Что отклоняется (сообщение называет причину; у отказов DT и 1CD по профилю конфигурации — ещё и код в квадратных скобках, например [compatibility_unverified]):
  - разностные, журнальные, шифрованные (в том числе TDE), составные и повреждённые копии — до восстановления, временная база не создаётся;
  - без --server: сжатые и зашифрованные копии и копии SQL Server старше 2014;
  - DT и 1CD: неприменённые расширения (ConfigCASSave, незавершённая реструктуризация NGS, схемы расширений кроме SchemaID 1), сторонние таблицы SQL (если не задан --ignore-extra-tables; не-dbo схемы и двойники X<N> отклоняются всегда), только старый список пользователей (users.usr) при пустой V8USERS, политики паролей и другие служебные данные, которые команда не переносит (сообщение перечисляет найденное);
  - DT и 1CD: режим блокировок не управляемый, режим совместимости 8.2.14 и ниже у любой конфигурации ([compatibility_old]) и вне 8.3.14–8.5.1 у конфигурации с общими реквизитами;
  - 1CD: режим совместимости ниже 8.3.11 (загрузка в 1CD принимает 8.3.11–8.5.1); этот отказ приходит уже после выгрузки из SQL Server;
  - DT и 1CD: копия с другой служебной строкой IBVersion; копии, записанные платформой 8.3.x, пока не проверены.
Проверено только на SQL Server 2022.

Подключение к SQL Server.
  --server передаётся sqlcmd как есть (-S): имя или адрес машины, имя\экземпляр или имя,порт.
  Без --user — доверенное подключение (Windows-аутентификация) под учётной записью, от которой запущен Yellowcode; на Linux и macOS без настроенного Kerberos нужен SQL-логин. С --user пароль берётся только из переменной SQLCMDPASSWORD.
  Соединение всегда шифруется; для самоподписанного сертификата (тестовый сервер, Docker) добавьте --trust-server-certificate.
  Если sqlcmd нет в PATH, укажите путь через --sqlcmd.

Прерывание и сбои. Имя временной базы — первая строка stderr. Ctrl-C или истёкший срок (одна команда sqlcmd — 30 минут, см. --sqlcmd-lifecycle-timeout) останавливают работу: временная база удаляется, результат не публикуется; если удалить её не удалось, сообщение называет базу и команду для администратора. После сбоя рядом с --output пишется отчёт yellowcode-bak-failure-<время UTC>.log: имена в нём заменены хешами (что скрыто и что нет — https://yellowcode.dev/guide/bak-failure-report/); --trace пишет такую трассу и при успехе.
