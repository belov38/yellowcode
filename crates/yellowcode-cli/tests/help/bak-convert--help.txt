Сохранить CF, DT или 1CD из копии MS SQL Server: через сервер (--server) или, только CF, прямым чтением файла

Usage: yellowcode bak convert [OPTIONS] --to <TO> --output <OUTPUT> <SOURCE>

Arguments:
  <SOURCE>  Путь к BAK: с --server — на машине SQL Server, без --server — локальный файл

Options:
      --platform-build <BUILD>
          Точная версия эмулируемой платформы (не режим совместимости конфигурации) [default: 8.5.1.1529]
      --server <SERVER>
          Сервер для sqlcmd -S: имя или адрес машины, имя\экземпляр или имя,порт (см. «Подключение к SQL Server» ниже); без него CF читается из файла напрямую
      --backup-set <BACKUP_SET>
          Номер набора резервной копии в BAK (позиция из RESTORE HEADERONLY) [default: 1]
      --to <TO>
          Формат результата [possible values: cf, dt, 1cd]
      --output <OUTPUT>
          Путь к новому файлу на машине с Yellowcode
      --user <USER>
          SQL-логин; пароль только из переменной SQLCMDPASSWORD; без --user — доверенное подключение (Windows-аутентификация)
      --sqlcmd <SQLCMD>
          Путь к Microsoft sqlcmd (ODBC); по умолчанию sqlcmd
      --sqlcmd-lifecycle-timeout <SQLCMD_LIFECYCLE_TIMEOUT>
          Общий срок каждой команды sqlcmd в секундах (по умолчанию 1800 + 120 на остановку); очистка получает отдельный срок
      --trust-server-certificate
          Доверять сертификату SQL Server без проверки его цепочки (нужно для самоподписанного сертификата, например в Docker)
      --trace <FILE>
          Записать трассу выполнения в новый файл и при успехе (или задайте переменную YELLOWCODE_TRACE)
      --memory-limit <MEMORY_LIMIT>
          Только для 1CD: бюджет памяти восстановления DT (auto или B/KiB/MiB/GiB); не ограничивает MS SQL Server
      --raw
          Только для CF: вернуть CONFIG как он хранится в базе, не применяя остатки динамического обновления
      --strict
          Только без --server: отказать, если CF нельзя доказать равным восстановленному SQL Server (журнал не применён, ADR, другая версия SQL Server), вместо предупреждения
  -h, --help
          Print help

Экспериментально. Копия восстанавливается во временную базу на вашем SQL Server, результат выгружается, база удаляется. CF: из полной копии, в том числе сжатой; если конфигурацию обновляли динамически, результат такой же, как выгрузка Конфигуратора, с --raw — как конфигурация хранится в базе. DT и 1CD: только небольшие базы без пользователей, базы типовых конфигураций отклоняются. Разностные, журнальные, шифрованные (в том числе TDE), составные и повреждённые копии отклоняются до восстановления. Проверено только на SQL Server 2022.

Без --server CF читается прямо из файла BAK, без SQL Server (только --to cf); журнал транзакций копии при этом не применяется. Если копия полная, несжатая и незашифрованная, одним файлом, сделана SQL Server 2022, без ускоренного восстановления базы (ADR), с контрольными суммами блоков журнала, а окно журнала в ней — только записи контрольной точки, CF совпадает с восстановленным SQL Server (в ответе proven: true). Иначе CF всё равно пишется, а в stderr выводится одна строка предупреждения: в базу писали во время копирования и журнал не применён (сколько записей), включён ADR (строки откаченных транзакций могут остаться в результате, а удалённые ими — пропасть), копию сделал SQL Server 2014–2019 или новее 2022, журнал не подтверждает прочитанное или у его блоков нет контрольных сумм; в ответе — proven: false, logApplied: false, logRecords и warnings с кодами (log_window_not_idle, log_not_proven, adr, sql_server_version, no_log_block_checksums). Точный вид в этих случаях даёт только --server. --strict вместо предупреждения отказывает с тем же кодом в квадратных скобках и подсказкой --server. Отклоняется всегда: сжатая или зашифрованная копия (compressed_or_encrypted), копия SQL Server старше 2014 (sql_server_version), разностная, журнальная и составная (striped) копии, повреждённые страницы и нарушения структуры, CONFIG, который отклоняет и SQL-путь; формы таблиц и страниц, которые читатель не разбирает, называются словами. Если такой отказ случился на копии, в которую писали во время копирования, строка в stderr говорит, что журнал не применён. Файл результата при отказе не создаётся. Проверено до 44 ГБ: CF побайтно совпал с CF через SQL Server в обоих видах (по умолчанию и с --raw) на 15 копиях баз 1С без нагрузки (БСП 3.1 и 3.2, ДО 2.1 и 3.0, ЗУП, УНФ, ERP, Бухгалтерия ПРОФ и КОРП; от 0,16 до 4,1 ГБ, сделаны SQL Server 2022 для Windows), на одной копии 44 ГБ (SQL Server 2022 для Linux) и на синтетических копиях. Читаются только каталог и таблицы конфигурации: на этих копиях — около 25 с и 100 МиБ памяти в худшем случае, на машине с быстрым локальным диском. В этом режиме SOURCE — путь к локальному файлу; --backup-set, кроме 1, а также --user, --sqlcmd, --sqlcmd-lifecycle-timeout, --trust-server-certificate, --memory-limit, --trace и переменная YELLOWCODE_TRACE не допускаются (трасса доступна только с --server), отчёт о сбое не пишется; --strict допускается только без --server. Всё, что ниже сказано о подключении к серверу, восстановлении, sqlcmd и отчёте о сбое, относится только к работе с --server.

Подключение к SQL Server.
Сервер: значение --server передаётся клиенту sqlcmd как есть (параметр -S), поэтому годится любая запись, которую принимает sqlcmd: имя или адрес машины (localhost, 127.0.0.1, sql01), именованный экземпляр (localhost\ИМЯ, sql01\ИМЯ), нестандартный порт (sql01,14330). Проверены две записи: 127.0.0.1 (SQL Server 2022 в Docker на той же машине, SQL-логин) и localhost\ИМЯ (именованный экземпляр на Windows, доверенное подключение); запись с портом и сервер на другой машине не проверялись. Команда подключается к базе master и ждёт входа не дольше 15 секунд.
Вход без --user: доверенное подключение (Windows-аутентификация, sqlcmd -E) под учётной записью, от которой запущен Yellowcode. На Linux и macOS оно без настроенного Kerberos не работает: там нужен SQL-логин.
Вход с --user: SQL-логин; пароль задаётся только переменной окружения SQLCMDPASSWORD (в командной строке его передать нельзя), без неё команда отказывает до подключения. В обоих случаях логину нужна роль sysadmin (см. ниже).
Шифрование: соединение всегда шифруется (sqlcmd -N). Если у сервера самоподписанный сертификат или имя в сертификате не совпадает с --server (обычно так у тестового сервера и у контейнера Docker), добавьте --trust-server-certificate (sqlcmd -C), иначе вход завершится ошибкой проверки сертификата. Флаг отключает проверку цепочки сертификата: используйте его только для своего тестового сервера.
Клиент: Microsoft sqlcmd на ODBC (mssql-tools18 или mssql-tools; проверены 18.7 на Linux и 16.0 на Windows) на машине с Yellowcode; если его нет в PATH, укажите путь через --sqlcmd. go-sqlcmd не подходит.
Пути: SOURCE — путь к BAK так, как его видит служба SQL Server на машине сервера (Yellowcode файл не копирует), --output — путь на машине с Yellowcode.
Примеры подключения:
  Windows, локальный именованный экземпляр, доверенное подключение:
    yellowcode bak convert 'C:\Backup\base.bak' --server localhost\SQL2022 --to cf --output base.cf
  Windows (PowerShell), SQL-логин:
    $env:SQLCMDPASSWORD = '<пароль>'; yellowcode bak convert 'D:\Backup\base.bak' --server sql01\SQL2022 --user yc_test --to cf --output base.cf
  Linux, SQL Server 2022 в Docker на той же машине, каталог с копией смонтирован в контейнер как /backup:
    SQLCMDPASSWORD='<пароль>' yellowcode bak convert /backup/base.bak --server 127.0.0.1 --user sa --trust-server-certificate --to cf --output base.cf

Путь SOURCE должен быть доступен службе SQL Server на машине сервера. Путь к копии может содержать знаки Юникода: на Windows проверены кириллица, апостроф, латиница-1 и эмодзи, на Linux кириллица, апостроф и эмодзи; путь не длиннее 259 единиц UTF-16 на сервере для Windows и 257 на сервере для Linux (SQL Server отвечает Msg 3057 на имя устройства длиннее 259); в сообщениях SQL Server на Windows знаки вне ANSI в имени показаны как ?: это ограничение клиента sqlcmd, сам путь передаётся верно. Измерено на одном стенде каждого вида.
Если BAK содержит несколько наборов, выберите позицию через --backup-set; по умолчанию используется первая. Набор должен быть полной копией; для CF выбор набора проверен на копии с несколькими наборами.
CF содержит основную конфигурацию, но не прикладные данные или расширения.
Принимаются полные копии одним файлом с одной data- и одной log-частью; сжатые допускаются. Разностные и журнальные наборы, шифрованные копии и TDE, составные (striped) копии и копии, помеченные повреждёнными в заголовке, отклоняются до восстановления: временная база не создаётся. Снимки отклоняются так же, но на настоящей копии-снимке это не проверялось. Недоступный файл и файл, который SQL Server не признаёт резервной копией, отклоняются при осмотре, тоже до восстановления.
Обрезанную копию SQL Server обнаруживает только при восстановлении (заголовки лежат в начале файла) и сам убирает за собой: очистка выполняется и её итог выводится.
Если выгрузка прервана на середине большого результата, сервер ещё какое-то время держит сеанс убитого клиента, и база «используется». Очистка отключает сеансы только этой временной базы (после проверки точного имени и метки этого запуска) и удаляет её; если база всё же осталась, сообщение называет её, её размер по каталогу (если размер узнать не удалось, так и пишет: size unknown) и команду для администратора: ALTER DATABASE [имя] SET SINGLE_USER WITH ROLLBACK IMMEDIATE; DROP DATABASE [имя]; (если ALTER не проходит, потому что база ещё в состоянии восстановления, выполните один DROP) — на любом пути сбоя очистки, в том числе когда сервер не ответил вовремя. База без метки этого запуска (запись метки не состоялась) командой не удаляется: сообщение просит проверить, что это ваша база, и даёт ту же команду.
Копия восстанавливается целиком: на сервере нужно место под всю базу (данные и журнал), даже если нужна только конфигурация.
На SQL Server для Windows восстановление включает обнуление файла журнала: у файлов журнала нет мгновенной инициализации, и для журнала в десятки гигабайт это минуты. На медленном диске срока по умолчанию (см. ниже) может не хватить.
CF и DT: CONFIG до 16 ГиБ, не более 1 млн файлов и 1024 частей на файл; строка ответа sqlcmd до 128 МиБ. Имена должны быть ASCII, Attributes — нулевым.
Файл CONFIG больше 10 000 000 байт платформа хранит частями; такой файл получает время создания, время изменения и атрибуты нулевой части, как в выгрузке самой платформы. Части должны идти подряд с 0 и совпадать по Creation, Attributes и DataSize, Modified не должно убывать от части к части; иначе команда отказывает и называет поле и номер части. Для CF проверено на пяти приватных копиях баз типовых конфигураций (62 таких файла): записи совпали с нативной выгрузкой 1С по имени, содержимому, времени создания и изменения и атрибутам, раскладка страниц контейнера отличается.
Динамическое обновление конфигурации при подключённом сеансе клиента не переписывает объекты в таблице Config, а оставляет рядом их копии (<объект>_dynupdate_<GUID обновления>, versions_dynupdate_…, deleted_dynupdate_…) и запись DynamicallyUpdated; платформа сама их не применяет, выгрузка Конфигуратора применяет. Для CF по умолчанию они применяются так же: содержимое объекта берётся из копии (время создания, время изменения и атрибуты остаются от объекта), копия без объекта добавляет его (время берётся из копии: время выгрузки в базе не хранится), deleted_dynupdate_… убирает названные записи, копии и запись DynamicallyUpdated в результат не попадают. Без записи DynamicallyUpdated результат не меняется. Когда что-то применено, в stderr печатается одна строка с числами (обновлений и операций: замен, добавлений, удалений), те же числа лежат в ответе stdout (dynamicUpdate). Флаг --raw возвращает CONFIG как он хранится в базе; с --to dt и --to 1cd он не допускается.
Правило проверено на платформе 8.5.1.1529 и SQL Server 2022 на пятнадцати контрольных образцах (до двенадцати динамических обновлений подряд, с заменой, добавлением и удалением объектов) и на одной настоящей базе: записи равны выгрузке Конфигуратора по имени, содержимому, времени создания и изменения и атрибутам (кроме времени добавленных объектов). Обновления применяются в порядке записи DynamicallyUpdated. Больше двенадцати обновлений подряд и случаи, которых образцы не показали или которых платформа сама не производит, команда отклоняет с причиной и номером обновления и предлагает --raw.
У баз с режимом совместимости ≤8.3.14 CF из BAK отличается от нативной выгрузки контейнером (Format16 вместо 15, раскладка TOC), записи равны.
1CD: CONFIG проходит через DT и загружается частями; действуют ограничения памяти и формата 1CD. Поддерживаемые локали: ru_RU, en_US.
DT/1CD: остальные файловые разделы — до 1024 частей и 64 МиБ на файл, с нулевыми Attributes; действуют ограничения на данные и память.
DT и 1CD — экспериментальный ограниченный перенос с управляемыми блокировками; обычные непустые пользователи и неподтверждённые хранилища не поддерживаются.
Разделённые пользователи поддерживаются при одном общем реквизите с разделением данных и совместимости 80501; остальные общие реквизиты не поддерживаются.
DT требует проверенный служебный профиль и целиком учитывает локальное двоичное хранилище.
Если восстановление прервано (клиент sqlcmd убит, истёк срок, потерян канал), команда удаляет незавершённую временную базу yc_bak_<токен> этого запуска из каталога сервера: только её, по точному имени (те же символы и та же длина) и только в состоянии восстановления. Удалить такую базу может только член роли sysadmin: другим логинам, владельцу базы включая, SQL Server отказывает в DROP, поэтому команда отклоняет логин без этой роли сразу, до создания временной базы (если роль отозвали во время работы, сообщение говорит, что базу и её файлы должен удалить администратор). Файлы прерванного восстановления SQL Server удаляет не всегда: сообщение называет оставшиеся файлы с путями и размерами по каталогу, их нужно удалить вручную на машине SQL Server. Удаление, очистка сеансов и проверка роли sysadmin проверены на SQL Server 2022 для Linux в Docker, с SQL-логинами. На одном экземпляре SQL Server 2022 Developer для Windows (один компьютер), с Windows-аутентификацией (логин с ролью sysadmin), проверено удаление базы в состоянии восстановления и в состоянии ONLINE, а также удаление временной базы после Ctrl-C, Ctrl-Break и закрытия окна консоли в обеих фазах (восстановление и выгрузка). Не проверялись: отказ логину без роли sysadmin на Windows, роль sysadmin через группу Windows, другие версии SQL Server, macOS.
Ctrl-C, SIGTERM и SIGHUP (на Windows: Ctrl-C, Ctrl-Break, закрытие окна консоли, выход из системы, выключение) во время работы с SQL Server команда обрабатывает как истёкший срок: останавливает свой клиент sqlcmd, удаляет временную базу теми же шагами, сразу пишет, что запрос принят, в конце сообщает итог очистки (если очистка не удалась, итог может занять несколько строк) и завершается тем же сигналом, а не кодом выхода: родитель, в том числе цикл оболочки, видит гибель от сигнала (оболочка показывает 130 для SIGINT, 143 для SIGTERM, 129 для SIGHUP; на Windows Ctrl-C и Ctrl-Break дают статус 0xC000013A; для закрытия окна, выхода из системы и выключения задуманы 129 и 143, но при закрытии окна процесс завершила сама Windows раньше, чем команда записала код, и статус в проверке не наблюдался). Результат (CF, DT или 1CD) не публикуется. Сигнал, который игнорировался при запуске (nohup, trap '' INT, фоновая задача неинтерактивной оболочки), остаётся игнорируемым: на него команда не реагирует и очистки по нему нет. Повторные сигналы во время очистки после прерывания игнорируются, а сама очистка ограничена 120 с на каждую команду; это больше срока, который дают docker stop (10 с по умолчанию) и systemd (90 с по умолчанию): при медленном сервере очистка может не успеть, процессу придёт SIGKILL, и база останется. Сигнал во время очистки после сбоя или после успешной выгрузки команда не игнорирует: первый она отмечает строкой (очистка продолжается), второй сигнал прекращает ожидание, и сообщение называет временную базу, её размер (или что он неизвестен) и команду для её удаления. Если сервер ещё восстанавливает базу (прерывание сразу после начала RESTORE), очистка повторяет попытки в пределах двух минут. Сигнал на локальном этапе DT в 1CD, который идёт после SQL-части и не наблюдается, обрывает команду сразу, как раньше, и оставляет рядом с результатом рабочие каталоги .yellowcode-*/source.dt и .yellowcode-restore-*/1Cv8.1CD; их можно удалить. Обработка сигналов проверена на Linux (SQL Server 2022 в Docker, SQL-логины) и на одном компьютере с Windows (SQL Server 2022 Developer, Windows-аутентификация). На Windows Ctrl-C и Ctrl-Break во время восстановления и во время выгрузки останавливают клиент sqlcmd (он делит консоль с командой), удаляют временную базу, результат не публикуется, процесс завершается статусом 0xC000013A, отчёт о сбое записан (исход failed, код 130); после прерванного восстановления SQL Server оставляет файлы базы (в проверке 6 ГБ журнала и 1 ГБ данных), сообщение называет их. Закрытие окна консоли завершает команду и клиент очистки за доли секунды, код выхода не наблюдался: временная база в проверке оказалась удалена, отчёта о сбое нет, файлы прерванного восстановления остаются; при закрытии окна, выходе из системы и выключении Windows даёт процессу лишь несколько секунд, поэтому очистка может не успеть. taskkill без /F ничего не делает (Windows отвечает, что процесс можно завершить только принудительно), запуск продолжается. Не проверялись: выход из системы и выключение, повторный сигнал во время очистки на Windows, Windows Terminal и PowerShell как родитель, macOS. Если процесс команды остановлен без возможности очистки (SIGKILL, потеря питания), ничего не удаляется: на Linux клиент sqlcmd доводит восстановление до конца, и остаётся база yc_bak_<токен> в состоянии ONLINE, только для чтения, с файлами полного размера; если клиент погиб вместе с командой, база остаётся в состоянии восстановления. На Windows проверена принудительная остановка процесса (taskkill /F): клиент погибает вместе с командой, и база остаётся в том состоянии, в котором её застала остановка (ONLINE, если восстановление уже закончилось; в состоянии восстановления, если оно шло). Имя базы выводится в stderr первой строкой каждого запуска. Удаление вручную от члена роли sysadmin: записать пути файлов (SELECT physical_name FROM sys.master_files WHERE database_id = DB_ID(N'yc_bak_<токен>')); если база в состоянии ONLINE, сначала выполнить ALTER DATABASE [yc_bak_<токен>] SET SINGLE_USER WITH ROLLBACK IMMEDIATE (иначе сеанс убитого клиента может удерживать базу: ошибка 3702); затем DROP DATABASE [yc_bak_<токен>]; и удалить записанные файлы, если они остались. На SQL Server для Windows это выполнено для базы в состоянии ONLINE (ALTER, затем DROP: база и её файлы исчезли) и для базы в состоянии восстановления (только DROP: он оставил два файла, и их удалили по записанным путям).
Нужен Microsoft sqlcmd (ODBC, пакет mssql-tools18) и логин с ролью sysadmin: команда восстанавливает временную базу и должна уметь её удалить, поэтому логин без этой роли отклоняется сразу, до создания временной базы, с сообщением «the login must have the sysadmin role on the test server». go-sqlcmd не подходит: версия 1.10 не принимает параметр -f.
Одна команда sqlcmd по умолчанию ограничена 30 минутами; срок меняет --sqlcmd-lifecycle-timeout. После сбоя удаление незавершённой базы и очистка получают не больше 2 минут каждое, и команда пишет в stderr, когда начинает каждое из них: если сервер завис, она кончается не позже чем через срок неудавшейся команды и ещё около четырёх минут. Очистка после успешной выгрузки этим пределом не ограничена: готовый результат ждёт её окончания, и она получает обычный срок команды (удаление большой базы может занять минуты). Если она не удалась, готовый результат (CF, DT или 1CD) не публикуется: команда завершается ошибкой, называет базу, её размер (или что он неизвестен) и команду для администратора.
Если команда не справилась уже после начала работы с SQL Server, она сама записывает отчёт о сбое yellowcode-bak-failure-<время UTC>.log рядом с --output (имена файлов, баз, серверов, логинов и путей в нём заменены хешами, но каталог или файл с именем из 1–3 цифр может остаться видимым в тексте сообщений; что скрыто и что нет — в docs/bak-failure-report.md) и печатает путь к нему. --trace ФАЙЛ или переменная YELLOWCODE_TRACE записывают такую трассу в указанный новый файл и при успешном завершении.
Пример: yellowcode bak convert 'C:\Backup\base.bak' --server localhost --to cf --output base.cf
Пример без SQL Server: yellowcode bak convert base.bak --to cf --output base.cf
